# 에이전트 출력 검토하기

에이전트 출력은 대체로 잘 쓰여 있고 대체로 맞다.
그래서 다시 볼 이유를 느끼지 못하고, 검토가 도장 찍기로 바뀐다.
출력이 검토 없이 다음 입력이 되는 순간, 책임은 이미 넘어간 것이다.

## 순서

1. **요약보다 증거를 먼저 본다.**
   실행한 명령과 출력, 테스트 결과, 측정값, 로그를 먼저 연다.
   보고에 증거 위치가 없으면 그것부터 요청한다.
2. **증거가 무엇을 증명했고 무엇을 증명하지 않았는지 적는다.**
   테스트 통과는 한 가지 속성만 말해 준다.
   테스트가 기능과 같은 실수를 품고 있으면 같이 통과한다.
3. **에이전트가 대신 내린 결정을 찾는다.**
   기본값, 범위에서 뺀 것, 요구가 부딪혔을 때 고른 쪽, 확인 없이 믿은 것을 본다.
   보고에 없으면 나열해 달라고 요청한다.
4. **숫자 하나, 원본 하나를 직접 확인한다.**
   결론이 기대는 숫자 하나를 골라 다시 계산한다.
   요약이 기댄 원본 문서나 데이터 몇 개를 직접 연다.
5. **완료 기준과 대조한다.**
   맡길 때 정한 기준을 다시 꺼내 하나씩 맞춘다.
   기준을 안 정하고 맡겼다면 지금 정하고, 사후에 정했다고 기록한다.

## 코드와 diff 를 볼 때

- AI 가 쓰지 않은 것처럼 읽는다. 변수 이름이 그럴듯하고 테스트가 통과해도 그것만으로 승인하지 않는다.
- 트랜잭션 경계, 순서, 기본값, 빈 입력이나 경계값 처리처럼 겉으로 티가 나지 않는 곳을 따로 본다.
- 무작위로 몇 줄을 골라 "왜 이렇게 했는가"에 답해 본다. 답하지 못하면 그 부분을 이해한 뒤에 승인한다.
- 이번 확인이 무엇을 놓칠지 말할 수 없으면, 빠른 승인 대신 제대로 된 리뷰를 한다.

## 요약과 조사 결과를 볼 때

- 원본 몇 개를 열어 요약이 맞는지 본다.
- 요약이 요약을 근거로 삼고 있지 않은지 본다. 세 번째 손을 거친 요약은 원본을 읽지 않은 상태일 수 있다.
- 형식이 매끄럽고 어조가 자신 있는 것은 품질의 신호가 아니다. 지금은 모든 출력이 그렇게 나온다.

## 양이 많을 때

에이전트로 무엇이 들어왔는지 분류하고, 내 주의가 필요한 곳을 좁히는 데 써도 된다.
최종 판단은 내가 한다.
들어오는 양이 내가 검토할 수 있는 양을 넘으면, 일을 더 맡기지 않고 검증을 자동화하거나 속도를 줄인다.

## 결과

검토를 마치면 세 가지를 남긴다.

```
판정: 받음 / 다시 요청 / 막음
확인한 증거: 무엇을 열어 봤는가
확인하지 않은 것: 이번 검토가 증명하지 않은 것
```

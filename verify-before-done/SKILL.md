# 끝내기 전에 점검하기

"끝났다"는 말은 사실이어야 한다.
끝난 것 같다는 느낌이나 초록불 하나로는 부족하다.
결과를 다른 사람이 감당한다면 더 그렇다.

## 점검 순서

1. **완료 기준과 대조한다.**
   맡을 때 정한 기준을 다시 꺼내 하나씩 맞춘다.
   기준이 없었으면 지금 적고, 사후에 정했다고 밝힌다.
2. **증거를 확인한다.**
   실행한 명령과 출력, 테스트 결과, 측정값, 로그를 다시 본다.
   기억이나 짐작으로 쓴 숫자는 보고에 넣지 않는다.
3. **증명하지 않은 것을 적는다.**
   테스트 통과는 한 가지 속성만 말해 준다.
   이번 확인이 놓칠 수 있는 것을 말할 수 없다면, 확인이 부족한 것이다.
4. **내가 내린 결정과 가정을 나열한다.**
   기본값, 범위에서 뺀 것, 요구가 부딪혔을 때 고른 쪽, 확인 없이 믿은 것을 적는다.
5. **숫자 하나, 원본 하나를 다시 확인한다.**
   결론이 기대는 숫자 하나를 다시 계산하고, 기댄 원본을 직접 연다.
6. **설명할 수 있는지 시험한다.**
   바꾼 것 가운데 몇 군데를 골라 "왜 이렇게 했는가"에 답해 본다.
   답하지 못하면 그 부분을 다시 이해한 뒤에 끝낸다.
7. **"놓친 게 있나?"를 묻는다.**
   복잡한 작업 끝에 이 질문을 하면 두세 가지가 더 나오는 일이 잦다.
   위험이 크면 새 컨텍스트의 서브에이전트에게 결과와 완료 기준만 주고 비판하게 한다.
   내 결론을 함께 주면 그 결론을 확인해 오기 쉬우니 주지 않는다.

## 위험도에 따라 깊이를 고른다

- 틀려도 되돌리기 쉬운 일: 1, 2, 3 만 한다.
- 운영 반영, 삭제, 돈, 다른 사람이 결과를 감당하는 일: 1에서 7까지 모두 한다.
- 애매하면 무거운 쪽으로 본다.

## 완료 보고 형식

```
상태: 끝 / 일부 / 막힘
바뀐 것: 파일, 커밋, 배포 같은 실체
증거: 실행한 명령과 출력 위치, 측정값
확인하지 않은 것: 이번 확인이 증명하지 않은 것
혼자 정한 결정과 가정:
결정 필요:
```

"확인하지 않은 것"이 비어 있으면 다시 본다.
비어 있는 경우는 드물다.

## 내보내지 않는 것

내가 설명할 수 없는 결과에는 이름을 붙여 내보내지 않는다.
언젠가 누군가는 그 결과에 대해 물어본다.

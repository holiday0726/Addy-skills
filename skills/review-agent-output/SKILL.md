# 에이전트 출력 검토하기

에이전트 출력은 대체로 잘 쓰여 있고 대체로 맞다.
그래서 다시 볼 이유를 느끼지 못하고, 검토가 도장 찍기로 바뀐다.
지난번 답을 꼼꼼히 읽었으니 이번 답은 훑어보고, 그다음은 뼈대만 본다.
출력이 검토 없이 다음 입력이 되는 순간, 책임은 이미 넘어간 것이다.

## 순서

1. **요약보다 증거를 먼저 본다.**
   실행한 명령과 출력, 테스트 결과, 측정값, 로그를 먼저 연다.
   보고에 증거 위치가 없으면 그것부터 요청한다.
2. **증명하지 않은 것을 묻는다.**
   보고의 체크가 무엇을 확인했고 무엇을 확인하지 않았는지 본다.
   보고에 "증명하지 않은 것"이 없으면 적어 달라고 한다.
3. **에이전트가 대신 내린 결정을 찾는다.**
   긴 작업 동안 에이전트는 작은 결정을 많이 내린다.
   기본값, 범위에서 뺀 것, 요구가 부딪혔을 때 고른 쪽, 확인 없이 믿은 것이다.
   보고에 없으면 나열해 달라고 한다.
4. **숫자 하나, 원본 하나를 직접 확인한다.**
   결론이 기대는 숫자 하나를 골라 다시 계산한다.
   요약이 기댄 원본 문서나 데이터 몇 개를 직접 연다.
5. **완료 정의와 대조한다.**
   맡길 때 정한 기준을 다시 꺼내 하나씩 맞춘다.
   기준 없이 맡겼다면 지금 정하고, 사후에 정했다고 기록한다.

## 코드와 diff 를 볼 때

- AI 가 쓰지 않은 것처럼 읽는다.
  변수 이름이 그럴듯하고 테스트가 통과해도 그것만으로 승인하지 않는다.
- diff 너머를 본다.
  트랜잭션 경계, 순서, 기본값, 빈 입력과 경계값처럼 겉으로 티가 나지 않는 곳을 따로 본다.
- 이번 확인이 무엇을 놓칠지 말할 수 없으면 빠른 승인 대신 제대로 리뷰한다.
- 승인하기 전에 내가 이 변경을 설명할 수 있는지 본다.
  설명할 수 없으면 rebuild-understanding 스킬로 필요한 조각을 다시 이해한다.

## 요약과 조사 결과를 볼 때

- 원본 몇 개를 열어 요약이 맞는지 본다.
- 요약이 다른 요약을 근거로 삼고 있지 않은지 본다.
- 매끄러운 형식과 자신 있는 어조는 품질의 신호가 아니다.
  지금은 모든 출력이 그렇게 나온다.

## 양이 많을 때

에이전트로 들어온 것을 분류하고, 가이드라인에 어긋나는 것과 내 주의가 필요한 곳을 좁히는 데 써도 된다.
최종 판단은 내가 한다.
그래야 그 변경이 맞는 문제를 맞는 방식으로 풀었는지를 실제로 생각할 수 있다.
들어오는 양이 검토할 수 있는 양을 넘으면 일을 더 맡기지 않는다.

## 검토 결과

```
판정: 받음 / 다시 요청 / 막음
확인한 증거: 무엇을 열어 봤는가
증명하지 않은 것: 이번 검토가 확인하지 않은 것
다시 요청할 것:
```

## 내보내는 글

이 스킬이 만드는 것은 사람이 읽는 글이다.
그래서 아래를 기본으로 지킨다.

- humanizer 스킬이 있으면 결과 글에 적용한다.
- 가운뎃점, 줄표(긴 것과 짧은 것), 화살표 기호를 쓰지 않는다.
- 하이픈으로 두 낱말을 잇지 않는다.
  ID, 경로, URL, 명령, 코드, 브랜치 이름처럼 원래 하이픈이 든 값만 그대로 둔다.
- 문장이 끝나면 줄을 바꾼다.
- 조어식 제목, 일상어 자리의 비유, 짜맞춘 대구, 아무도 하지 않은 말을 부정하며 시작하는 대조, 과장, 앞 문장을 되풀이하는 맺음을 쓰지 않는다.
- 다 쓴 뒤 금지 문자가 남았는지 검사한다.

```bash
# 가운뎃점, 줄표, 화살표
grep -nP '[\x{00B7}\x{2010}-\x{2015}\x{2190}-\x{21FF}]' <파일>
# 낱말을 잇는 하이픈
grep -nP '[가-힣A-Za-z]-[가-힣A-Za-z]' <파일>
```

두 번째 검사에 걸린 줄 가운데 ID, 경로, URL, 명령, 코드, 브랜치 이름만 남기고 나머지는 고친다.

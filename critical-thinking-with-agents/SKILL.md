# 에이전트 시대의 비판적 사고

에이전트가 일을 할수록 비판적 사고는 저절로 일어나지 않는다.
출력이 매끄럽고 대체로 맞아서, 다시 볼 이유를 느끼지 못하기 때문이다.
이 스킬은 그 사고를 세 지점에 일부러 넣는다.

1. 일을 맡길 때
2. 내 일을 끝낼 때
3. 사람의 큰 결정을 도울 때

## 먼저 판단할 것: 위임의 단계와 위험도

위임에는 세 단계가 있다.

| 단계 | 모습 |
|---|---|
| 오프로딩 | 일은 맡기고, 결과에 대한 책임과 이해는 내가 쥔다 |
| 추종 | 출력이 검토 없이 다음 입력이 된다 |
| 항복 | 출력이 그대로 내 것이 되고, 확인할 생각도 하지 않는다 |

목표는 오프로딩에 머무는 것이다.
판단 기준은 하나다.
에이전트의 도움을 받아도 이 결과를 설명할 수 없다면, 이미 책임을 넘긴 것이다.

모든 일에 같은 깊이로 점검하지 않는다.
틀려도 되돌리기 쉽고 비용이 작은 일은 가볍게 본다.
운영 반영, 데이터 삭제, 돈, 다른 사람이 결과를 감당하는 일은 아래 절차를 끝까지 밟는다.
어느 쪽인지 애매하면 무거운 쪽으로 본다.

## 1. 일을 맡길 때

배정서는 내 이해를 드러낸다.
명확하게 쓸 수 없다면 내 머릿속에서도 명확하지 않은 것이다.
에이전트는 모호한 요청을 되묻지 않고 빈칸을 채워 완성된 것처럼 돌려준다.
그래서 빈칸은 맡기기 전에 내가 채운다.

배정서에 아래를 넣는다.

```
목표: 이 일이 끝나면 무엇이 달라지는가
내 가설: 결과가 어떨 것이라고 보는가 (틀려도 된다)
범위 밖: 하지 말 것, 건드리지 말 것
완료 기준: "검증됨"이 무엇인지. 어떤 명령, 테스트, 측정값이 나와야 끝인가
원본: 읽어야 할 원본 문서와 데이터 경로 (내 요약이 아니라)
보고 형식:
  - 실행한 명령과 출력이 남은 위치
  - 확인하지 않은 것
  - 혼자 정한 결정과 가정
  - 결정이 필요한 것
```

왜 이렇게 하는가.

- **가설을 먼저 적는다.** 잘 쓰인 답을 한 번 읽으면 다른 가능성을 떠올리기 어렵다. 실마리가 없으면 아는 것을 주고 "내가 모르는 줄도 모르는 것"을 찾아 달라고 따로 요청한다.
- **완료 기준을 미리 정한다.** 끝난 뒤에 정하면 어떤 결과든 합리화하게 된다. 완료 기준은 해석이 아니라 테스트 통과, 측정값, 로그처럼 실체가 있는 것이어야 한다.
- **원본을 넘긴다.** 에이전트끼리 요약만 넘기면 세 번째 에이전트는 원본을 읽지 않은 상태가 된다. 내 요약은 길잡이로만 붙인다.
- **보고에서 받을 칸을 미리 요구한다.** "다 잘 됐다"는 요약에는 에이전트가 대신 내린 작은 결정(기본값, 범위에서 뺀 것, 충돌하는 요구 중 고른 쪽)이 보이지 않는다.

맡기기 전에 한 가지를 더 본다.
지금 받아서 검토할 여력이 있는가.
에이전트가 만드는 양이 내가 책임질 수 있는 양보다 많아지면, 일을 더 늘리지 않는다.
검증을 자동화해 내 손이 덜 가게 하거나, 속도를 줄인다.

## 2. 내 일을 끝낼 때

"끝났다"고 말하기 전에 아래를 차례로 한다.
보고를 받아 검토할 때도 같은 순서로 본다.

1. **완료 기준과 대조한다.** 맡을 때 정한 기준을 다시 꺼내 하나씩 맞춰 본다. 기준이 없었으면 지금 적고, 사후에 정했다고 밝힌다.
2. **요약보다 증거를 먼저 본다.** 실행한 명령과 그 출력, 테스트 결과, 측정값, 로그를 먼저 확인한다. 기억이나 짐작으로 쓴 숫자는 쓰지 않는다.
3. **초록불이 증명한 것과 증명하지 않은 것을 적는다.** 테스트 통과는 한 가지 속성만 말해 준다. 테스트가 기능과 같은 실수를 품고 있으면 같이 통과한다. 이번 확인이 놓칠 수 있는 것을 말할 수 없다면, 가벼운 확인으로 끝내지 말고 제대로 검토한다.
4. **내가 내린 결정과 가정을 나열한다.** 기본값, 범위에서 뺀 것, 요구가 부딪혔을 때 고른 쪽, 확인 없이 믿은 것을 적는다.
5. **숫자 하나, 원본 하나를 직접 확인한다.** 결론이 기대는 숫자 하나를 골라 다시 계산하고, 요약이 기댄 원본 몇 개를 직접 연다.
6. **설명할 수 있는지 시험한다.** 바꾼 것 가운데 몇 군데를 골라 "왜 이렇게 했는가"에 답해 본다. 답하지 못하면 그 부분을 다시 이해한 뒤에 끝낸다.
7. **"놓친 게 있나?"를 묻는다.** 위험도가 높으면 새 컨텍스트의 서브에이전트에게 결과만 주고 비판하게 한다. 내 결론을 함께 주면 그 결론을 확인해 오기 쉬우니, 결과와 완료 기준만 준다.

완료 보고는 이 형식으로 쓴다.

```
상태: 끝 / 일부 / 막힘
바뀐 것: 파일, 커밋, 배포 같은 실체
증거: 실행한 명령과 출력 위치, 측정값
확인하지 않은 것: 이번 확인이 증명하지 않은 것
혼자 정한 결정과 가정:
결정 필요:
```

"확인하지 않은 것"이 비어 있으면 다시 본다.
비어 있는 경우는 드물다.

## 3. 사람의 큰 결정을 도울 때

결정은 사람의 몫이다.
무엇을 만들지, 왜 가치가 있는지, 누구에게 영향을 주는지, 무엇을 희생할지는 에이전트가 대신 정하지 않는다.
에이전트는 사람이 스스로 판단할 수 있게 재료를 정리한다.

1. **내 가설을 먼저 적는다.** 그다음에 근거를 모은다.
2. **"이게 틀리려면 무엇이 참이어야 하는가"를 적고 실제로 확인한다.** 확신도를 말로 매기는 것보다, 실행할 수 있는 확인 하나가 훨씬 값지다.
3. **반대편을 세운다.** 강한 입장일수록 반대 논거를 따로 만들거나 다른 모델, 다른 관점에 반대편을 논증하게 한다.
4. **원본을 직접 본다.** 결론이 기대는 숫자와 문서는 요약이 아니라 원본에서 확인한다.
5. **선택지는 결과로 쓴다.** 고르면 무엇이 일어나고, 무엇을 잃는지 적는다. 추천이 있으면 하나만 표시하고 이유를 붙인다.
6. **모르는 것을 밝힌다.** 확인하지 못한 것, 어림한 숫자, 문서끼리 어긋나는 곳을 따로 적는다.

## 기준에 못 미친 것을 남긴다

결과가 기준에 못 미쳤으면 이유를 적고, 다시 일어나지 않게 남긴다.
남기는 곳은 공유 설정, 훅, 테스트, 메모리처럼 다음 작업이 실제로 읽는 곳이다.
무엇이 왜 탈락했는지 적는 일이 안목을 쌓는다.

## 하지 않는 것

- 위험이 작은 일에 이 절차를 전부 돌리지 않는다. 언제 깊이 들어갈지 고르는 것도 판단이다.
- 매끄러운 형식과 자신 있는 어조를 품질의 신호로 보지 않는다. 지금은 모든 출력이 그렇게 나온다.
- 내가 설명할 수 없는 결과에 내 이름을 붙여 내보내지 않는다.

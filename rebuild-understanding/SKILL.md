# 이해 다시 세우기

에이전트의 도움을 받아도 결과를 설명할 수 없다면, 책임은 이미 넘어간 것이다.
이렇게 쌓이는 것이 이해 부채다.
코드는 깔끔해 보이고 테스트도 통과해서 당장은 보이지 않는다.
무언가를 바꿔야 할 때가 와서야 아무도 그것을 이해하지 못한다는 것이 드러난다.

큰 코드베이스 전체를 머릿속에 들고 있을 수는 없다.
그럴 필요도 없다.
필요할 때 필요한 조각을 다시 세우면 된다.
다만 무엇을 모르는지는 알아야 한다.

## 1. 무엇을 모르는지 찾는다

바로 설명을 쏟아 내지 않는다.
먼저 사용자에게 짧은 질문 두세 개를 던져 어디까지 아는지 본다.

- 이 변경은 무엇을 하려는 것인가
- 이걸 바꾸면 무엇이 깨지는가
- 이 숫자는 어디에서 오는가

답하지 못한 곳이 다시 세울 조각이다.

## 2. 필요한 조각만 다시 세운다

전체를 설명하지 않고 그 조각만 설명한다.
순서는 이렇게 한다.

1. 목적: 이 부분이 왜 있는가
2. 구조: 무엇에 기대고, 무엇이 이것에 기대는가
3. 세부: 실제 코드나 문장, 원본 위치

전문 용어가 나오면 한 줄 정의로 넘기지 않는다.
그 개념이 이 일의 어디에 들어맞는지까지 설명한다.

## 3. 변경 보고서와 퀴즈를 만든다

긴 세션을 마치거나 큰 변경을 병합하기 전에 만든다.

```
바뀐 것: 동작이 어떻게 달라졌는가
에이전트가 내린 결정과 가정: 기본값, 범위에서 뺀 것, 요구가 부딪혔을 때 고른 쪽
퀴즈:
  1. 무작위로 고른 줄 하나: 이 줄은 왜 이렇게 됐는가
  2. 이 기본값을 바꾸면 무엇이 달라지는가
  3. 이 변경이 다루지 않는 경우는 무엇인가
정답: 사용자가 답한 뒤에 보여 준다
```

사용자가 원하면 "퀴즈를 모두 맞혀야 병합한다"는 규칙을 둔다.
틀린 문항은 2번으로 돌아가 그 조각을 다시 세운다.

## 4. 문서는 기억으로 써 보게 한다

문서를 승인하기 전, 사용자에게 문서를 닫고 핵심 논지를 기억만으로 써 보게 한다.
에이전트는 그 글을 원문과 대조해 빠진 것과 틀린 것을 알려 준다.
목차만 읽고 승인하는 일을 막는다.

## 5. 연습하지 않게 된 것을 점검한다

쓰지 않는 기술은 생각보다 빨리 사라진다.
놓아도 되는 기술도 있지만, 의도해서 놓아야 한다.
사용자가 원하면 주기 점검을 돕는다.

- 한 달에 한 번: 에이전트에게 맡기게 되어 더 이상 하지 않는 일을 적고, 그중 무엇을 놓아도 괜찮은지 사용자가 정한다.
- 일주일에 한 번: 잊으면 곤란한 작은 일 하나를 에이전트 없이 해 본다.
- 가끔 묻는다: AI 가 없다면 이 일에서 얼마나 헤맬 것인가.

에이전트는 제안만 하고, 무엇을 계속 연습할지는 사용자가 정한다.

## 내보내는 글

이 스킬이 만드는 것은 사람이 읽는 글이다.
그래서 아래를 기본으로 지킨다.

- humanizer 스킬이 있으면 결과 글에 적용한다.
- 가운뎃점, 줄표(긴 것과 짧은 것), 화살표 기호를 쓰지 않는다.
- 하이픈으로 두 낱말을 잇지 않는다.
  ID, 경로, URL, 명령, 코드, 브랜치 이름처럼 원래 하이픈이 든 값만 그대로 둔다.
- 문장이 끝나면 줄을 바꾼다.
- 조어식 제목, 일상어 자리의 비유, 짜맞춘 대구, 아무도 하지 않은 말을 부정하며 시작하는 대조, 과장, 앞 문장을 되풀이하는 맺음을 쓰지 않는다.
- 다 쓴 뒤 금지 문자가 남았는지 검사한다.

```bash
# 가운뎃점, 줄표, 화살표
grep -nP '[\x{00B7}\x{2010}-\x{2015}\x{2190}-\x{21FF}]' <파일>
# 낱말을 잇는 하이픈
grep -nP '[가-힣A-Za-z]-[가-힣A-Za-z]' <파일>
```

두 번째 검사에 걸린 줄 가운데 ID, 경로, URL, 명령, 코드, 브랜치 이름만 남기고 나머지는 고친다.
